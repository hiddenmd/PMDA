# PMDA — Post-Mission Data Analysis — Design

Date: 2026-10-17
Status: Sections 1, 3 (slice 1) and 4 (web slice 1) approved; section 2 and 5 are working defaults.

## Goal

Import binary flight recordings from three customers into SQL Server as a single
common, time-ordered event stream (emitter detections, countermeasures, nav,
warnings, ...), and analyse them from both a desktop and a web frontend.

## Constraints

- Input: binary files described by an ICD. 50 MB – 1 GB, 1–50 M events per flight.
- Three customers. Content is broadly the same; file headers / record framing differ.
- Backend C# (.NET 9). Database: SQL Server.
- Frontends: desktop and web, both high-performance on dense timelines.
- Assumption: one deployment + database per customer (data never mixed).

## Architecture (approach 1: modular monolith + shared core)

```
PMDA.Core      event model, interfaces. No dependencies.
PMDA.Parsers   shared payload decoders + per-customer adapters (header/framing)
PMDA.Import    streaming import pipeline (adapter -> decoders -> sink)
PMDA.Data      SQL Server: schema, SqlBulkCopy sink, query layer (Dapper)
PMDA.Api       ASP.NET Core: import, window queries, aggregates        (later)
PMDA.Desktop   Avalonia + GPU chart; can host the API in-process       (later)
PMDA.Web       React + TS + WebGL chart against PMDA.Api               (later)
```

## Section 1 — Event model + parser plugin (approved)

Pipeline: `file -> ICustomerAdapter -> IPayloadDecoder(s) -> FlightEvent stream -> sink`

- `ICustomerAdapter` — `CanRead(fileStart)` for auto-detect, `ReadHeader`, `ReadRecords`
  yielding `RawRecord(MessageType, TimestampTicks, Payload)`. Framing only.
- `IPayloadDecoder` — one per message type, shared across customers. A customer
  may register an override decoder for a message type whose layout differs.
- `FlightEvent` — FlightId, Seq, TimeUtc, EventType, SubType, EmitterId, Frequency, Pri,
  PulseWidth, Bearing, Amplitude, Lat, Lon, Alt, Count, Extra (raw leftovers).
  SubType/Count cover countermeasures (e.g. chaff vs flare, number dispensed).
- Parsing with `Span<byte>` / `BinaryPrimitives`, no per-record allocation in hot paths.
- Corrupt records: logged with file offset and skipped; import continues.
- Customer auto-detected from header, manual override allowed.

## Section 2 — Import & storage (proposed)

- Stream the file; never load it whole. Events batched (default 102 400 — the minimum bulk
  insert that SQL Server compresses directly into a columnstore rowgroup) to an `IEventSink`.
- SQL sink uses `SqlBulkCopy` into `FlightEvent` table with a clustered columnstore index.
- `Flight` table: FlightId, CustomerId, Tail, MissionId, StartUtc, EndUtc, SourceFile,
  FileSha256, ImportStatus, EventCount, ErrorCount.
- Re-import of a file with same SHA-256 is rejected (idempotent).
- Import is all-or-nothing per flight: failure marks the flight Failed and deletes its rows.

## Section 3 — API (approved, slice 1: imports + flights)

`PMDA.Api`, ASP.NET Core 9. OpenAPI document generated by the app, Swagger UI at `/swagger`.

| Endpoint | Purpose |
|---|---|
| `POST /api/imports` | multipart upload, streamed to a temp file (no 1 GB buffering) → `202 { importId }` |
| `GET /api/imports` / `GET /api/imports/{id}` | job status + progress; polling fallback for the client |
| `DELETE /api/imports/{id}` | cancel |
| `GET /api/flights?page&pageSize&customer&tail` | paged list |
| `GET /api/flights/{id}` | details |
| `GET /api/flights/{id}/diagnostics` | parse problems (new `ImportDiagnostic` table) |
| SignalR `/hubs/imports` | pushes `ImportUpdated` (state + progress) for every change |

Server import state machine: `Queued → Running → Completed | Duplicate | Failed | Cancelled`;
`Queued → Cancelled` also allowed; every other transition throws. Jobs flow through a bounded
`Channel` into a `BackgroundService` running at most `MaxConcurrentImports` at once. Job state is
held in memory (lost on restart; flights themselves are in SQL).

Layers: endpoints (thin) → application services → `PMDA.Import` / `PMDA.Data`.
Errors as `ProblemDetails`. DTOs separate from domain types. Strongly typed options.
Database: local SQL Server 2025, Windows auth; `PMDA` for the app, `PMDA_Test` for tests.

Later slice: `GET /flights/{id}/events?from&to&types&limit` and
`GET /flights/{id}/timeline?from&to&buckets=N` (server-side downsampling).

## Section 4 — Frontends

Web client (approved, slice 1), `web/`: Vite + React + TypeScript.
- Typed API: `openapi-typescript` types generated from the OpenAPI document + `openapi-fetch`.
- Server state: TanStack Query (flights list/details, invalidated when an import completes).
- State machines, XState v5:
  - `importMachine`: `idle → uploading(%) → queued → processing(%) → completed | duplicate | failed`,
    `cancel` from active states → `cancelled`, `retry` from `failed`. Updates come from the hub;
    when the hub is not connected it polls `GET /api/imports/{id}`.
  - `connectionMachine`: `disconnected → connecting → connected → reconnecting`, backoff; drives a
    status indicator.
- Hooks: `useImport()`, `useImportHub()`, `useFlights()`, `useFlight(id)`. Components render state and
  send events; no logic in JSX.
- Layout: `api/`, `machines/`, `hooks/`, `features/imports`, `features/flights`, `components/`.

Later: desktop (Avalonia, GPU chart), timeline view with WebGL chart (SciChart.js or uPlot).

### Slice 2: redesign + debrief playback (approved)

Visual system: `design-system/pmda/MASTER.md` (ui-ux-pro-max "Data-Dense Dashboard", dark default,
bundled Fira Sans/Code, Lucide icons). Layout: left rail (import, flights list) + flight workspace
(header KPIs, RWR scope, active emitters, countermeasures, position, transport bar with density strip
and scrubber, collapsible parse problems).

Playback never streams raw events (600× is ~120 000 events per real second). The server returns frames:
- `GET /api/flights/{id}/frames?from&to&stepMs` — per step: per emitter avg frequency/PRI/PW/amplitude,
  circular-mean bearing (`ATN2(AVG(SIN), AVG(COS))`), hit count; countermeasure counts by kind; last
  position. `from`/`to` are offsets in ms from flight start; max 2 000 steps per request.
- `GET /api/flights/{id}/overview?buckets=N` — event counts per type per bucket across the flight.
The client picks `stepMs ≈ speed × 33 ms` (about 30 frames per real second).

`playbackMachine` (XState): `loading → ready.{paused | playing | buffering} → ended`; events PLAY, PAUSE,
SEEK, SET_SPEED, STEP, TICK (requestAnimationFrame clock actor). Prefetches ahead of the playhead;
enters `buffering` when the playhead reaches the end of loaded frames; SEEK drops stale requests.
Emitters stay active for a persistence window after their last frame (max(3 s, 4 steps) of flight time).
Scope: canvas, 60 fps, RWR convention (stronger signal nearer the centre). Text panels ~10 Hz.
Keyboard: Space play/pause, ←/→ step, `[` `]` speed; scrubber is a native range input.

Samples: `tools/PMDA.SampleGen` simulates a mission (ground emitters with fixed sites and parameters, an
aircraft route, geometry-derived bearing and amplitude, countermeasures on close threats) and writes the
standard set to `samples/` (not committed): training-sortie, dense-threat, corrupt-records, long-mission.

## Section 5 — Testing (proposed)

- Parsers: unit tests on hand-built byte buffers per message type and per adapter,
  including corrupt/truncated records.
- Pipeline: tests with an in-memory sink.
- Data + API: integration tests against local SQL Server (`PMDA_Test`), API via `WebApplicationFactory`.
- Web: Vitest for machines (pure, no DOM) and hooks/components with React Testing Library.
- Performance benchmark: synthetic 50 M-event file, target import < 5 min.
